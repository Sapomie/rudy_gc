# 后端 API 优化总方案

## 1. 文档定位

本文档用于指导 `api/` 后端的持续优化，覆盖普通 HTTP 请求、后台任务、SSE、数据库、缓存、文件操作和外部抓取链路。

本方案衡量的是用户请求延迟、数据访问成本、失败恢复能力、资源占用和代码可维护性。代码行数、文件数量和重构规模不作为优化结果。任何性能结论都必须来自相同环境、相同数据和相同请求条件下的优化前后测量。

配套文档：

- [API 现状清单](./api_inventory.md)：记录当前接口、调用链和已核实风险。
- [API 优化进度](./progress.md)：记录基线、实施、验证、失败和回退。

## 2. 优化目标

### 2.1 请求性能

- 降低高频列表、详情和聚合接口的响应延迟。
- 降低单次请求的数据库往返、重复读取和响应组装成本。
- 避免缓存异常时出现逐项回源和查询数量放大。
- 控制大候选集合在数据库、网络和 Go 内存之间的搬运成本。

### 2.2 正确性

- 保持现有路由、参数、响应字段、排序、分页和业务语义。
- 优化前后使用响应摘要和关键字段断言证明结果一致。
- 写操作必须明确事务边界、部分失败、缓存失效和重试结果。
- 文件操作必须覆盖数据库与文件系统状态不一致时的恢复路径。

### 2.3 稳定性

- 后台任务能够正确启动、暂停、恢复、停止和退出。
- SSE 连接断开后释放订阅、Ticker 和 Goroutine。
- MySQL、Redis、外部站点或文件系统异常时返回可识别结果。
- 后台任务的资源使用不能无依据地挤占普通请求。

### 2.4 可维护性

- Handler、Service 和 Repository 的职责可定位、可测试。
- 共享数据组装、参数解析和错误映射只保留一个权威实现。
- 结构调整在性能和契约稳定后进行，并单独验证。

## 3. 证据规则

文档和实施记录使用三种状态：

| 状态 | 含义 | 允许的表述 |
| --- | --- | --- |
| 已核实事实 | 已读取代码、执行命令或请求真实接口 | 明确写出检查对象、方法和结果 |
| 待验证假设 | 代码形态显示可能存在风险，但尚无运行数据 | 写出验证方式，禁止表述为已发生问题 |
| 已验证结果 | 已完成前后对照和正确性验证 | 写出环境、参数、指标和证据位置 |

以下内容不能作为性能完成依据：

- 代码成功编译。
- 单元测试通过。
- 文件被拆分或代码量减少。
- SQL 数量减少但总耗时、扫描量或响应结果未验证。
- 缓存代码存在但命中、失效和异常回退未验证。
- 单次请求变快但重复测量和页面完整链路未验证。

## 4. 当前基线

### 4.1 已核实事实

- Router 当前注册 152 条路由：GET 74、POST 67、PUT 5、DELETE 6。
- 后端主要调用链为 `transport/http -> service -> repository/model -> MySQL/Redis/文件系统/外部站点`。
- 数据层同时使用 go-zero `CachedConn`、无缓存查询接口和独立的 MovieType Redis 缓存。
- `ListMovieFull` 取得当前页标识后，会逐项调用 `GetMovieType` 组装完整卡片。
- `GetMovieType` 缓存读取失败或未命中后，会从多个 Model 读取电影、演员、类型、排名和媒体信息。
- 复杂列表查询同时存在单表查询、候选集合运算、子查询和 SQL `JOIN`。
- 聚合功能同时存在在线计算和聚合结果表读取。
- Crawler 提供任务启动、状态控制、事件历史和 SSE 推送。
- 现有测试文件 34 个，没有 Go Benchmark。
- Router 测试覆盖少量关键路由，没有覆盖全部 152 条路由的快照。
- `router.go` 207 行，`list_pages_api.go` 2307 行，`movie_list_query.go` 2083 行，`svc/deps.go` 270 行。
- 2026-07-16 执行 `go test -count=1 ./...`、`go vet ./...` 和 `go build ./cmd/api` 均通过。

### 4.2 尚未验证

- 152 条接口的真实调用频率和用户等待时间。
- 核心接口的 P50、P95、P99、SQL 数量、数据库耗时和响应体积。
- MovieType 缓存的实际命中率、错误率和回源成本。
- 复杂筛选候选集合在真实数据规模下的行数、内存和耗时。
- 存量 `JOIN` 迁移为单表查询后的性能变化。
- 后台任务运行时对普通 API 延迟、数据库连接和磁盘 IO 的影响。
- SSE 连接数量、持续时间、重连频率和断开后的资源释放。
- 前端完整页面加载产生的并行请求总耗时。

因此，当前状态只能作为代码与构建基线，不能宣称后端性能已经优化。

## 5. 实施约束

- 可由现有缓存满足的读取优先使用缓存。
- 缓存键必须包含稳定的数据身份和版本信息；所有相关写入口必须定义失效范围。
- 缓存未命中或异常时使用批量数据库回退，避免按列表项逐个回源。
- 新代码严禁使用 SQL `JOIN`；存量 `JOIN` 按业务链路逐项迁移。
- 跨表筛选通过各表独立批量查询候选标识，并在 Go 中完成集合运算。
- 单表查询必须先约束候选范围、使用已有索引并验证执行计划，禁止无依据地读取完整表。
- 不新增分页、并发、候选数量、事件历史或响应结果的阈值和静默截断。
- 不把结构重构与性能逻辑改动混在同一个验证单元。
- 不修改当前任务范围之外的 `web/`、部署或数据。
- 不执行不可逆的媒体移动、删除或数据库清理作为普通验收手段。

## 6. 优先级判定

优化顺序由证据决定，不按文件大小或实现难度决定。

每个候选接口记录以下信息：

- 用户是否直接等待结果。
- 页面或任务是否高频调用。
- 请求是否产生逐项查询、重复查询或大候选集合。
- 缓存异常是否会放大数据库访问。
- 是否占用数据库连接、网络、磁盘或大量内存。
- 失败是否会造成数据不一致或不可恢复的文件状态。
- 是否存在可重复的基准和契约验证方法。

首批候选来自电影卡片、电影详情、电影相册、FC2 列表、SC 事件、媒体列表和抓取任务状态等真实页面链路。最终先后顺序由基线结果确定。

## 7. 优化工作流

### 7.1 建立可重复基线

对进入优化范围的接口固定记录：

- 代码版本与配置文件。
- 数据库与缓存实例。
- 数据规模摘要和关键表行数。
- 请求方法、路径、查询参数和请求体。
- 缓存状态：热缓存、冷缓存、缓存异常。
- 请求执行方式和重复次数。
- P50、P95、P99、平均值、最大值和错误数量。
- SQL 次数、SQL 总耗时、最慢 SQL 和执行计划。
- 缓存命中、未命中、错误和回源次数。
- 响应大小、响应摘要和关键字段。
- Go 内存分配、GC 和 Goroutine 变化。

请求次数和测试持续时间在执行时记录真实值，并在优化前后保持一致；方案不预设新的固定阈值。

### 7.2 优化读取与响应组装

目标是让一次列表请求按数据类型批量读取，而不是按列表项重复执行完整详情链路。

实施步骤：

1. 从基线中找出 SQL 数量与页内项目数量同步增长的接口。
2. 列出响应字段及其数据来源。
3. 为当前页标识设计各数据源的批量读取方法。
4. 在 Service 中建立请求级映射并一次性组装响应。
5. 保留单资源详情读取方法，列表链路不循环调用详情方法。
6. 对空关联、重复关联和缺失数据建立契约测试。
7. 对比优化前后的 SQL、延迟、内存和响应摘要。

首要待验证链路是电影列表的 `ListMovieFull -> GetMovieType -> buildMovieTypeFromModels`。该链路的代码形态具备查询数量随缓存状态变化的风险，但必须通过基线确认实际影响。

### 7.3 治理缓存

缓存优化以正确性和可降级性为前提：

1. 盘点现有 go-zero Model 缓存和独立业务缓存。
2. 明确每类缓存保存的对象、键、版本、有效期和数据来源。
3. 建立命中、未命中、反序列化失败和 Redis 失败的测试场景。
4. 为列表链路提供批量读取或请求级合并，避免重复访问相同缓存键。
5. 所有新增、修改、删除和批量操作同步定义缓存失效。
6. 缓存失败时进入批量单表读取，并验证响应一致性。
7. 分别测量热缓存、冷缓存和异常回退，不用热缓存结果代表全部场景。

### 7.4 治理复杂筛选与排序

复杂查询按“候选生成、集合运算、排序分页、详情补全”分解：

1. 为每个筛选条件标记所属数据表和可用索引。
2. 各表独立返回最小候选标识集合。
3. 在 Go 中执行交集、并集或排除。
4. 由排序字段所属表完成最终排序与分页。
5. 当前页结果再进入批量详情组装。
6. 对候选数量、数据库返回字节、集合运算分配和总耗时做完整记录。
7. 使用真实 `EXPLAIN` 验证每条单表 SQL。

迁移存量 `JOIN` 时一次只处理一个调用链。迁移前保存响应结果和执行计划，迁移后验证结果、排序和性能；性能恶化时保留失败记录并回退该实现。

### 7.5 治理聚合与统计

聚合接口按实时性拆分：

- 必须实时的数据：使用受索引约束的单表统计和批量集合计算。
- 可以延迟的数据：使用已有聚合结果表、增量更新或显式回填任务。
- 页面展示数据：优先读取已生成结果，避免请求内重复扫描源表。

实施时记录源数据版本、聚合范围、生成时间和读取时间。回填任务必须可重复执行，失败后能够识别未完成范围。

### 7.6 治理写操作

写操作按数据库写入、缓存失效、文件操作和任务触发拆解：

1. 明确输入校验与目标集合。
2. 明确事务覆盖的表和事务外操作。
3. 批量操作避免循环内独立提交。
4. 数据库提交后执行准确的缓存失效。
5. 文件移动先形成可审查计划，再执行并记录结果。
6. 文件成功而数据库失败、数据库成功而文件失败都必须有恢复方案。
7. 重复请求验证幂等结果，禁止制造重复关系或重复任务。

### 7.7 治理后台任务与 SSE

任务与普通请求分别测量：

- 任务创建、状态转换和最终状态。
- 重复任务识别。
- 暂停、恢复、停止的实际生效点。
- 上下文取消与服务退出。
- 事件历史、订阅注册和取消。
- SSE 连接断开后的 Channel、Ticker 和 Goroutine。
- 任务运行期间普通接口的延迟、数据库连接和 IO 变化。

任务性能优化必须同时保证任务结果完整，不能通过静默减少处理范围获得更短耗时。

### 7.8 统一契约与错误边界

在核心性能链路稳定后，盘点参数校验、状态码、错误字段和底层错误暴露：

- 同类错误具有一致的 HTTP 状态和响应字段。
- 参数错误不会继续进入 Service。
- 数据库、文件系统和外部站点错误保留服务端上下文，客户端获得稳定分类。
- 成功响应不因错误治理改变字段和空值语义。

契约调整必须先建立 Handler 测试，并同步验证当前前端调用。

### 7.9 结构与测试能力

结构治理只解决定位、依赖和测试隔离问题：

- 拆分承担多个领域职责的超大 Handler 文件。
- 将共享响应组装提取为可测试组件。
- Service 构造函数接收实际使用的依赖集合。
- 为路由建立完整方法与路径快照。
- 为集合运算、排序和批量组装增加 Benchmark。

结构改动前后必须保持路由、响应和性能基线；结构调整不声明性能收益。

## 8. 分阶段实施

| 阶段 | 目标 | 主要交付物 | 退出条件 |
| --- | --- | --- | --- |
| 0. 基线 | 建立事实与测量能力 | 路由清单、核心请求样本、数据规模、契约摘要、基准脚本 | 核心链路可重复测量 |
| 1. 列表读取 | 消除高成本逐项组装 | 批量 Repository、批量 Service 组装、契约测试 | SQL、延迟、响应一致性完成对比 |
| 2. 缓存 | 稳定热路径与异常回退 | 缓存清单、批量读取、失效测试、降级测试 | 三种缓存状态均有结果 |
| 3. 查询与聚合 | 控制候选、排序和统计成本 | 单表查询、集合运算、执行计划、聚合读取 | 结果一致且资源成本有证据 |
| 4. 写入与任务 | 提升一致性和运行稳定性 | 事务测试、幂等测试、任务状态与 SSE 释放测试 | 失败与退出路径可验证 |
| 5. 契约与结构 | 降低维护风险 | 错误契约测试、路由快照、职责拆分 | 全量回归和关键页面通过 |
| 6. 收口 | 验证整体效果 | 最终基准、回归报告、剩余风险、回退说明 | 文档与实际代码完全一致 |

阶段顺序可以根据真实基线调整，但任何阶段都不能跳过本阶段的优化前测量、正确性验证和优化后测量。

## 9. 单项任务模板

每个实施任务按以下结构记录：

1. 任务编号和接口范围。
2. 当前调用链。
3. 已核实问题或待验证假设。
4. 数据规模与请求样本。
5. 优化前指标。
6. 计划修改文件和行为影响。
7. 实施内容。
8. 优化后指标。
9. 响应一致性、数据库结果和文件结果。
10. 测试与构建。
11. 风险、失败记录和回退方式。
12. 最终状态。

## 10. 回退规则

出现以下情况时停止当前实现并回退本任务改动：

- 响应字段、顺序、空值或业务结果发生未计划变化。
- 热缓存改善但冷缓存或缓存异常显著放大数据库访问。
- SQL 次数下降但扫描量、总耗时或内存成本恶化。
- 单表候选查询返回过多数据，Go 集合运算成为新的主要成本。
- 写操作产生部分成功且没有恢复路径。
- 后台任务无法停止、SSE 资源无法释放或服务退出被阻塞。
- 测试、竞态检测、静态检查或构建失败。

回退后在进度文档保留基线、失败指标、原因和已撤销文件，避免重复采用相同错误路径。

## 11. 验证矩阵

| 范围 | 必须验证 |
| --- | --- |
| 普通查询 | 状态码、字段、排序、分页、空结果、延迟、SQL、缓存、响应大小 |
| 复杂筛选 | 单条件、组合条件、大候选、无候选、集合结果、排序稳定性 |
| 详情接口 | 主资源缺失、关联缺失、缓存状态、响应完整性 |
| 写操作 | 参数错误、成功、重复请求、部分失败、事务、缓存失效 |
| 聚合 | 数据范围、重复执行、增量与全量一致、读取延迟 |
| 后台任务 | 重复启动、状态转换、暂停、恢复、停止、退出、资源竞争 |
| SSE | 初始历史、实时事件、重连、断开、订阅释放、Ticker 释放 |
| 文件操作 | 计划、冲突、源文件变化、目标存在、失败恢复 |

## 12. 交付标准

最终交付必须包含：

- 当前代码对应的完整接口清单。
- 核心接口的优化前后实测结果。
- 缓存三种状态的行为与性能证据。
- 所有新增单表 SQL 的真实执行计划。
- 响应和数据结果一致性证据。
- 自动化测试、竞态检测、静态检查和构建结果。
- 真实页面关键链路验证。
- 未验证项、剩余风险和可执行回退说明。

缺少上述证据的任务只能记录为进行中或待验证，不能记录为完成。
