# 数据库、缓存与性能规则

## 查询设计

- 写 SQL 前先明确：主表、过滤条件、排序字段、分页方式、返回列、数据量级。
- 索引必须按 `WHERE + ORDER BY + LIMIT` 一起设计，不能只覆盖过滤或只覆盖排序。
- 只取需要的列，避免无意义 `SELECT *`。
- 能按单表索引完成的请求，不要强行走连表、子查询或通用交集流程。
- 纯单源请求必须走单源快路径。

## 缓存规则

- 唯一查询能走缓存方法时必须走缓存方法，例如 `FindOne`、`FindOneByX` 或项目等价封装。
- 不能为了省事使用 no-cache 查询绕过唯一索引缓存。
- 直接迁移、回填、脚本、手工 SQL 或批量直写后，必须清理受影响缓存。
- 写操作必须走项目统一写路径，保证缓存失效一致。

## 高风险 SQL

以下情况必须在方案里说明表、索引和风险：

- 连表查询。
- `IN (...)`，尤其是大列表。
- `EXISTS` / `NOT EXISTS`。
- 聚合、分组、去重。
- 排序分页。
- 范围查询叠加排序。
- 可能产生 `Using filesort` 或临时表。

## 性能反例

- 先全量取集合，再二次查询同一张表分页。
- 对纯单源请求仍然计算多个空集合再求交。
- 在已经有主键/唯一缓存查询时改写成直查。
- 使用 `album_id IN (...) ORDER BY sort_col` 这类无法稳定利用索引顺序的全局排序，却没有说明执行计划。
- 在分页查询里加入语义上冗余的 `IN (finalIDs...)`，导致索引退化。

## 设计原则

- 能走缓存一定走缓存。
- 走不了缓存必须有索引。
- 需要跨多个有序来源时，优先考虑每个来源按索引顺序取数，再在应用层做有限归并。
- 如果必须接受 `filesort`、临时表或大范围扫描，必须明确说明原因、数据量和替代方案。
